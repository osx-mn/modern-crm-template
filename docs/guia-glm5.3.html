Antes de nada

🗺️ El mapa del monorepo

Un solo repositorio, tres mundos: lo que ve el usuario (web), lo que responde (api) y donde viven los datos (db). Regla de oro: el navegador nunca habla con la API directamente — siempre pasa por Next.js.

Árbol real de tu proyecto (los colores indican de quién es cada cosa)

modern-crm-template/
├─ apps/
│  ├─ web/        NEXT.JS  ← frontend · puerto 3000
│  └─ api/        NESTJS + PRISMA  ← backend · puerto 4000
├─ docs/          MVP.md · PLAN-COMPLETO.md · esta guía
├─ docker-compose.yml  DOCKER  ← solo la BD · puerto 5432
├─ justfile       JUST  ← comandos con nombre
├─ .gitignore     protege .env y node_modules
└─ .env.example   plantilla de variables SIN valores reales

¿Por qué dos apps separadas?

El frontend (Next) y el backend (Nest) tienen vidas distintas: el primero se preocupa de pantallas y experiencia; el segundo, de reglas, permisos y datos. Separados, cada uno escala, se despliega y se razona por su lado. Y cualquier cliente (web, móvil, otro servicio) podría usar la misma API.

¿Quién habla con quién?

Navegador → Next.js (3000). Next reenvía /api/* → NestJS (4000). Nest → Prisma → PostgreSQL (5432, dentro de Docker). Nadie más entra a la base de datos.

Frontend

▲ Next.js

Un framework de React. React solo sabe pintar componentes en el navegador; Next añade lo demás: rutas por carpetas, render en servidor, optimización, y en tu caso un proxy hacia la API.

Analogía: es la vitrina y el mostrador de una tienda. El cliente (navegador) solo trata con el mostrador. Si el pedido necesita cocina, el mostrador lo lleva atrás (rewrites) y trae el plato — el cliente nunca entra a la cocina.

La idea clave del App Router: la carpeta ES la URL

src/app/
├─ layout.tsx      ← marco común de TODAS las páginas
├─ page.tsx        ← URL:  /
├─ customers/
│  ├─ page.tsx     ← URL:  /customers
│  └─ [id]/
│     └─ page.tsx  ← URL:  /customers/abc123
└─ login/
   └─ page.tsx     ← URL:  /login

Cuando llegues al Día 1 y crees customers/page.tsx, esa URL ya existe. Sin configurar nada.

Tus rewrites: el proxy que evita el dolor de cookies

async rewrites() {
  return [{
    source: "/api/:path*",
    destination: API_URL + "/:path*",
  }];
}

El navegador pide /api/customers al puerto 3000. Next lo reenvía en silencio al 4000. Como todo ocurre en el "mismo origen", la cookie httpOnly del login (corte 1) funcionará sin configuración extra de CORS.

Para la entrevista: "Uso Next.js con App Router: cada carpeta dentro de src/app es una ruta; layout.tsx envuelve todas las páginas; y reenvío las llamadas a la API con rewrites para que frontend y backend compartan origen."

Backend

🐱 NestJS

Un framework para construir APIs en Node con estructura obligatoria: todo se organiza en módulos, y cada petición pasa por un camino predecible. Si Next es el mostrador, Nest es la cocina: pedidos que entran, estaciones organizadas, recetas que se siguen.

El recorrido de una petición DENTRO de Nest (de derecha a izquierda cuando la construyas, de izquierda a derecha cuando la leas)

HTTP → main.ts (puerta) → AuthGuard (¿quién eres? · corte 1)
     → ValidationPipe (¿los datos son válidos?)
     → Controller (recibe el pedido, decide quién lo cocina)
     → Service (lógica de negocio)
     → PrismaService (habla con la BD) → JSON de vuelta

Módulos: cajas que agrupan

Todo en Nest vive en un @Module. El AppModule es la caja raíz; dentro importaste ConfigModule (variables de entorno) y tu PrismaModule. Cuando hagas clientes, crearás un CustomersModule con su controller y su service — y lo registrarás ahí.

Inyección de dependencias (DI)

No creas servicios con new: los declaras y Nest los construye y reparte. Tu PrismaService está decorado con @Injectable() y exportado desde un módulo @Global(): por eso mañana cualquier service podrá pedirlo en su constructor sin duplicar conexiones.

Para la entrevista: "NestJS estructura el backend en módulos con controllers (HTTP), services (lógica) y DI. bootstrap() es solo el nombre convencional de la función que arranca la app. El ValidationPipe con whitelist descarta campos que no declaré en el DTO — validación en el servidor, siempre."

Datos · capa de acceso

🔷 Prisma

Un ORM: defines tu base de datos en un archivo de texto (schema.prisma) y Prisma te da, a cambio, un cliente TypeScript tipado para leer y escribir sin escribir SQL a mano — y migraciones para que los cambios de esquema queden versionados en Git.

Analogía: es un intérprete con contrato firmado. Le pides un pedido en TypeScript y él traduce a SQL, ejecuta, y te devuelve objetos con tipos garantizados. Si pides algo que no existe en el contrato, tu editor te avisa antes de correr el código.

Tú escribes (TypeScript)
prisma.customer.findMany({
  where: { ownerId: userId },
  include: { notes: true },
  orderBy: { createdAt: "desc" },
})
Prisma ejecuta (SQL)
SELECT *, (notas de cada cliente)
FROM "Customer"
WHERE "ownerId" = $1
ORDER BY "createdAt" DESC;

El pipeline: dos comandos, dos salidas

schema.prisma  (el mapa, en código)
   │
   ├─ npx prisma migrate dev  → crea el SQL en la BD real
   │                            + guarda la migración en prisma/migrations/
   │
   └─ npx prisma generate     → genera el cliente tipado
                                en src/generated/prisma/ (gitignored)
Para la entrevista: "El schema es la fuente de verdad. Con Prisma 7 la conexión vive en prisma7.config.ts y el cliente usa driver adapters (@prisma/adapter-pg). El dinero va en Decimal, nunca Float; los borraos son en cascada desde Customer; y el índice @@index([ownerId]) existe porque TODA consulta filtra por dueño."

Datos · el almacén

🐘 PostgreSQL

La base de datos relacional más usada del mercado: datos en tablas con filas y columnas, relaciones entre ellas, y el lenguaje SQL. Madura, estricta y confiable — el estándar contra el que se mide todo lo demás.

Tus 4 tablas y sus relaciones

User 1 ──── * Customer  (ownerId: "mis clientes")
                  ├─ 1 ──── * Note   (cascade)
                  └─ 1 ──── * Deal   (cascade)
                                    con stage: LEAD→CONTACTED→PROPOSAL→WON→LOST

Cascade significa: si borras un Customer, sus Note y Deal se borran solas — sin registros huérfanos. Lo verificaste en tu checklist del Flujo 3.

Una fila de Customer, de verdad

id        "cmh2xk9f1000"   ← cuid()
name      "TechStore S.A."
email     "ventas@techstore.com"
phone     "+507 6000-0000"
ownerId   "user_abc..."    ← TODA consulta filtra por esto
createdAt 2026-09-30 19:26
updatedAt 2026-09-30 19:26  ← @updatedAt: automático
Por qué Decimal y no Float: Float redondea mal el dinero (0.1 + 0.2 ≠ 0.3 en binario). Decimal(12,2) guarda exactamente los centavos. Clásico de entrevista.

Infraestructura

🐳 Docker

Empaqueta software con todo su entorno en contenedores aislados. Una imagen es la plantilla (la "clase"); un contenedor es una instancia corriendo (el "objeto").

Analogía: contenedores de carga marítima. PostgreSQL llega dentro de su caja, con su configuración, sin importar si tu máquina es Windows, Mac o Linux. No instalaste Postgres en Windows — y de hecho, te salvó: tu Postgres nativo viejo ocupaba el puerto 5432 y Prisma le hablaba a él, no al tuyo.

Tu docker-compose.yml, línea por línea

services:
  db:
    image: postgres:17          ← la plantilla oficial, versión 17
    environment:
      POSTGRES_USER: crm        ← credenciales SOLO de desarrollo
      POSTGRES_PASSWORD: crm_dev_password
      POSTGRES_DB: crm          ← crea esta BD al arrancar
    ports:
      - "5432:5432"             ← puertoHost:puertoContenedor
    volumes:
      - pgdata:/var/lib/postgresql/data   ← ¡los datos viven FUERA del contenedor!
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U crm"]  ← ¿estás vivo?
      interval: 5s
      retries: 10

volumes:
  pgdata                        ← el disco persistente

El truco del volumen

Puedes hacer just db-down (destruir el contenedor) mil veces: los datos están en el volumen pgdata, en tu disco. Cuando el contenedor vuelva a nacer, se reconecta a ese mismo volumen. Contenedor efímero, datos permanentes.

Los comandos que ya usas

docker compose up -d db   ← crear/arrancar (-d: segundo plano)
docker compose ps         ← ¿corre? ¿healthy?
docker compose down       ← parar y quitar (datos → volumen)
docker compose exec db psql ...  ← entrar a la BD

Productividad

🔧 just

Un corredor de comandos escrito en Rust (pariente moderno de make). Le das nombres a los comandos que siempre olvidas, y los ejecutas con just nombre. Tu justfile funciona igual en Windows, Mac y Linux.

Anatomía de una receta

# API en modo dev (puerto 4000)     ← comentario = la documentación
[working-directory: 'apps/api']     ← just entra aquí por ti (agnóstico del shell)
api:                                  ← nombre de la receta
    npm run start:dev                 ← una línea = un comando simple

Por qué es portable: sin cd X && Y (eso depende del shell) y con set windows-shell para que Windows use PowerShell mientras Mac/Linux usan sh.

Tu rutina diaria con just

just db      # terminal 1
just api     # terminal 2
just web     # terminal 3

Cuando toques el schema

just migrate  # aplica cambios
just generate # regenera el cliente
just studio   # mira los datos
